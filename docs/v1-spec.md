# unpack: v1 Features & Data Model (v1.2, approved direction, Oct 27, 2026)

## v1 features

**Teacher (Clerk login)**
1. Sign up or log in with Google or email.
2. Create a class, which gets a short join code (free plan: 1 class). The teacher sets the class's **grade level**, which questions and nudges are written for.
3. Add a reading by pasting a link (we extract the text) or pasting text directly.
4. The teacher picks the **number of questions** (1–10, default 3) and a **question mode**:
   - **Same for everyone:** generated once. The teacher can review, edit, and regenerate before publishing.
   - **Unique per student:** each student gets their own AI-generated set when they first open the reading, which makes it harder to share answers. The teacher can view each student's set afterward.
5. Publish the reading to the class.
6. Class progress: each student on each published reading shows as Not started, In progress, Waiting for teacher, Passed, Challenged, or Challenge denied, with tries used. Each reading's column header says how many passed, "0 of 2 students passed", counted with the same status rule the student sees. A table on wide screens, one card per student on narrow ones. A student who used every try at getting their own questions for a reading (per-student mode) shows **Needs a reset** instead of Not started, with "Their questions didn’t load." and a neutral **Let them try again** button. Each student's name opens their own page: the same statuses per reading, and for Needs a reset a plain explanation and the same button. Teachers see student answers (PR 15): on a published reading's page, **Student answers** lists every student (name, status, tries), and each one who tried opens to every question with their answer on each try, **Passed** or **Not yet** (icon and word), "Kept from try N" for a passed answer carried over, and the latest tip they were shown; the student's page has **See answers** under each reading they tried, the same view. The queries are owner scoped in the SQL (the class and the signed-in teacher; reading and student ids only narrow it), so another teacher's class, reading, or student matches nothing, and no self-learner table is read.
7. Challenge queue (with a count on the class page): for each open challenge, the student (first name and initials), the reading, their note, every question with their last try's answer, the effort check's pass or fail and nudge per answer, and tries used (not checks). Then one of three buttons: **Accept** (counts as Passed), **Deny**, or **Deny, give one more try**. The queue also lists each student who is out of tries (or at the check limit) on a published reading with no note yet, the class view's Waiting for teacher, as one row with an amber **Out of tries, no note yet** pill, tries used, "Name can still send you a note.", **See answers** (their page, with that reading's answers open), and **Give one more try** (secondary, not red or amber; screen readers hear "Give one more try for Name on Reading"; "Giving…" while it saves). That button is "Deny, give one more try" without a note: the same grant and limits, below. "Let them try again" is only for Needs a reset, so it isn't offered. It is counted on the class page like a challenge and sorted with them, oldest first by when the student started waiting (the note's time, or their last try or counted check). It leaves the queue when the student sends a note (then it is listed once, as the challenge), passes, or gets one more try (from a denied note, or from Give one more try on the row; the queue's live region then says "One more try given. Name has 1 more try."); it comes back if that try is used without a pass and no new note. Nothing is stored for the row itself; students see "Send your teacher a note." with "Your teacher can also give you another try."
8. Join code settings on the class page: a switch to turn the code on or off, and **New code** (with a quick confirm) to replace it.
9. Delete one student and all of their work, from Class progress (a red Delete, then a confirm dialog with "Delete {name}"). A second click (two tabs, say) is a no-op success. See [Student data and privacy](privacy.md).
10. Delete a reading, from its page (Delete reading, then a confirm dialog with a red **Delete** and a neutral Cancel, saying that students' answers and tries for it are lost and it can't be undone). Afterward the teacher is back on the class page with "Reading deleted, with its questions and every student’s answers and tries."
11. Class settings on the class page: the class name and grade level, one **Save changes**. Picking a different grade while drafts would lose their questions shows an amber note first, with how many.
12. A per-student reading near or at its student limit shows a note on its page ("This reading is almost full (140 of 150 students)", "This reading is full (150 students)") and a neutral **Raise the limit to 300**, once per reading. After that the page shows "Limit raised to 300 students", from 285 of 300 an amber "This reading is almost full (290 of 300 students)" with a note that the limit was raised once already and can't go higher (no button), and once 300 students have a set, "This reading is full (300 students)" with the same note (no button). On the class page's reading list, a per-student reading near its limit (from 135 of 150, or 285 of 300) has an amber "Almost full" badge, and one at its limit a neutral "Full" badge; the counts are read out to screen readers.

**Student (no account)**
1. Enter the class code, their **first name, and the first 1–2 letters of their last name** (for example "Maya Ro"). This creates a browser session, and progress is tied to that session, not to the name.
   - If that name is already taken in the class, the student is asked to add another letter.
   - A student on a new device starts fresh. Progress does **not** carry over by name.
2. See the class's published readings.
3. Read in a clean view with copy and paste blocked.
4. Answer the questions and submit. The AI returns pass or fail per answer, with a short nudge on each fail.
5. Up to 3 tries. A question that passes is done: on later tries it shows read-only with its answer, and only the "not yet" questions are answered again (see Answers and tries below). After the 3rd fail (or once every effort check is used without a pass), they can submit a challenge note to the teacher.
6. Passed readings are marked done, showing the passing answers, with a small celebration (PR 15): a burst of stars (CSS animation, about 1.8s, played once when the celebration is on screen; right after a passing check the page scrolls it into view, since the questions sit below the reading; still stars under reduced motion) and a short line, "First try! You really dug into that one." or "You kept going and got there. That’s how strong readers grow." (not when the teacher accepted a note). Self-learners get the same on a pass. The class home shows each reading as Not started, In progress, Send your teacher a note (out of tries or checks, no note yet), Waiting for your teacher (a note sent), Passed, or Challenge denied. Right after the last try or check with no note yet, the reading page leads with "Send your teacher a note." and, under it, "Your teacher can also give you another try." (the teacher's Give one more try), then the note box; its live region says "That was try 3 of 3. Send your teacher a note. Your teacher can also give you another try." (or "That was your extra try. ..." or "We couldn’t check your answers. ..."). Once the note is sent it shows the "Waiting for your teacher" badge. Self-learners (/learn/r) have no teacher, so none of this applies there. An In progress or Waiting row also says how far along it is, "2 of 3 done": the answers that passed on the latest try (the same count as the reading page's "Not yet. 2 of 3 answers passed."), out of the reading's question count. Passed answers are locked and carried into every later try, so this is also every question passed so far, and it never goes down.
7. When the teacher decides: Accept shows the reading as Passed ("Your teacher accepted your answers."); Deny shows a kind message and no form; Deny with one more try brings the answer form back with "1 try left".

**Account roles (PR 13)**
1. Every Clerk account has one row in `teachers` (the table keeps its name) with a **role**: teacher or self-learner. Accounts from before PR 13 were backfilled to teacher (migration 0008), so existing teachers see no prompt. A new account starts with no role.
2. Routes: `/home` sends each account to its home (no role: `/welcome`; teacher: `/teacher`; self-learner: `/learn`). Sign-in and sign-up are our own pages, `/sign-in` and `/sign-up` (Clerk's `<SignIn />` and `<SignUp />` on catch-all routes, public in src/proxy.ts; never Clerk's hosted pages), and both land on `/home`. The landing page's Get started opens `/sign-up` and Sign in opens `/sign-in`. While `/home` and `/welcome` load right after the email code, they show the sign-in loading card ("Getting your account ready…", PR 15). Signing out (the account menu) lands on the landing page `/` (`afterSignOutUrl` on ClerkProvider, PR 15), never Clerk’s Account Portal. Clerk telemetry is off. The account menu’s avatar image has an empty alt when the account has no name (Clerk would say "’s logo"; the menu button has its own label). `/welcome` is the first-run choice: two big cards, "I’m a teacher" and "I’m reading for myself", then Continue. `/settings` switches the role. `/learn/**` is the self-learner area: home, `/learn/new`, `/learn/r/{id}`, `/learn/history`. `/teacher/**` stays the teacher area. All of these require a Clerk session (src/proxy.ts).
3. Role rules, enforced on the server in every page, layout, and server action (not just the UI): no role goes to `/welcome` from everywhere; a self-learner opening any teacher page or posting any teacher action is sent to `/learn`; a teacher opening `/learn` is sent to `/teacher` (Settings is linked in the teacher header to switch). Self-learner queries read only the signed-in account's own `self_*` rows, never classes, readings, or students; another account's self-learner reading is a 404.
4. Age (neutral age screen, PR 15, following the FTC’s COPPA guidance): choosing "I’m reading for myself" (at first run, or in Settings the first time) shows **"When were you born?"** with two selects, Birth month and Birth year (placeholders "Month" and "Year", no default, years from this year back 100), and the neutral line "We ask everyone who reads on their own. We don’t save your answer." Nothing on the page names the cutoff or the right answer. A blank, out-of-range or future answer gets the one error "Choose a month and a year." **Server rule** (`checkAgeScreen`, src/lib/age-screen.ts): born in month M of year Y counts as 13 or older only from the month after M of year Y + 13 (UTC), so the person is 13 for every day of the current month whatever their birth day; the 13th birthday month itself counts as under 13. The UTC month is safe in every time zone (when UTC is in the next month, local time is at worst the last day of the birthday month). **Under 13:** the server sets the cookie `unpack_age_gate=under` (30 days, httpOnly, SameSite=Lax, Secure in production, no date or age in it). We don't keep under-13 accounts: an under-13 result deletes the account right away. On `/welcome` (no role yet) the action deletes our row and everything under it (the Clerk webhook's delete, limited to a row with no role, behind the same account lock, listing the id's hash), then the Clerk account (`users.deleteUser`, tried twice; the webhook's later delivery is a no-op); a local failure still deletes in Clerk, and a Clerk failure is retried on the next sign-in to that account. Deleting the user in Clerk ends their sessions, and the action redirects to `/join` (no sign-out step in the page), whose heading reads "Let’s get you into a class" while the cookie is set. The server log gets one fixed `under13_account_delete` line, never an id, email, name, month or year. While the cookie is on the device, both the `/welcome` and the `/settings` actions refuse self-learner without reading any answer (Back, reload, or picking again doesn’t retry). **Teacher role:** while the cookie is set, an account with no role can't pick teacher either: `/welcome` shows only the class note with **Join with a code** (no cards, no Continue), and the action refuses any choice. An account that already has a role is unaffected: a teacher stays a teacher everywhere, Settings included (an under-13 answer there sets the cookie and refuses self-learner, nothing is deleted). An account that confirmed 13+ before isn’t asked, and the cookie doesn’t affect it. We store only `age_confirmed_at` (when), never the month, the year, or a birthdate. The role and the timestamp are written by one statement that refuses a self-learner without a confirmation (now or before), and a database check constraint is the backstop. Teachers don't need it. Switching back to self-learner later doesn't ask again, and the first confirmation time is kept.
5. Switching (Settings): keeps all data and only changes which home the account sees. A teacher who switches keeps their classes (students can still join and work; the teacher just doesn't see the class pages until they switch back), and a self-learner who switches keeps their readings. Switching back restores access. A teacher switching to self-learner confirms it first (PR 14): pressing Save shows an amber note ("Your classes stay open": classes and join codes stay live, students can still join and keep working, and they can switch back any time to get to their classes) with **Switch to reading for myself** and **Keep teaching**; the server action refuses that switch without the confirm and shows the same note. Shown to every teacher who switches, whether or not they have classes. It is one UPDATE (race-safe), and choosing the current role again is a no-op. The first-run choice saves only while no role is set, so two tabs can't both choose.

**Self-learner (PR 13)**
1. New reading (`/learn/new`): paste a link or text, the same form, validation, and link reading (safeFetch, the 20 per 10 minutes link limit, keyed by the account) as the teacher's; pick a **reading level** (required, from the grade levels) and the number of questions (1 to 10, default 3). No question mode.
2. Questions: written once for that account's reading, the first time its page opens, and cached. A claim on the reading row makes two tabs write at most one set; each write counts toward the account's question generation limit (30 per 10 minutes, the teacher limit reused). A failed write saves nothing and shows Try again; past the limit, an amber note: "You’ve asked for a lot of questions in the last 10 minutes, so let’s take a short break. You can try again at 2:40 PM." (see Limits and retry times).
3. Answers: the student read view (copy and paste blocked), the same answer form and effort check (one check per try, one at a time, 6 checks per reading, counting only checks the model answered, 60 seconds), nudges, **3 tries**, and the same lock on passed questions (later tries answer only the "not yet" ones). A pass marks the reading **Passed**. After the 3rd failed try (or once every check is used without a pass) the page shows the last try's answers with nudges, and the reading is marked **Moved on**, with buttons to start a new reading or see history. There is **no challenge step**: no note, no challenge rows, no extra try.
4. Allowance: **5 new readings per rolling 7 days** on the free plan (`allowanceFor(plan)`; only free exists; paid is TBD). Counted from `self_readings` rows by `created_at`: self-learners can't delete readings, so the rows are the creation log (if a delete is ever added, count from a separate log). The create locks the account row and inserts only while fewer than 5 were created in the window, so concurrent creates can't make more than 5. At the limit the page shows a calm amber note, "You’ve read 5 this week. Your next one frees up on Friday at 9:30 AM." (today/tomorrow/weekday, from the oldest creation in the window plus 7 days, formatted on the server in the visitor's zone from Vercel's `x-vercel-ip-timezone`, else UTC labeled "UTC"). A reading exactly 7 days old no longer counts. A reading whose question write fails doesn't use a slot (PR 15): only when a write was attempted (claimed, counted toward the question limit, model called) and failed, for any reason (including a 402 or a provider outage), is the reading's slot released (`slot_released_at`) while it has no questions. An open that doesn't call the model keeps its slot (PR 16 review A1): not set up, the account's question limit, another tab's write in progress. That reading gets its questions on a later open (Try again after the wait, or once question writing is set up) with the slot it kept. Releasing there let an account at its question limit create, open (rate limited, slot back) and repeat past the 5; a release after a failed write is bounded by the question limit, since every attempt counts toward it. So while claimed writes keep failing (a timeout, a 402, a provider error), each failed reading gives its slot back and readings are capped by the question limit (30 per 10 minutes), not by the 5 slots (PR 16 review N5). Its Try again takes the slot back inside the claim, under the same account lock as the create and only while a slot is free; with none free, the page shows the allowance note instead of calling the model. So creates and Try agains together never hold more than 5, and a reading with questions always holds its slot. (Counting only readings with questions instead would let a burst of creates all pass before any had questions.)
5. History (`/learn/history`, and the latest 3 on `/learn`): every reading, newest first, with title, date, level, and result (Passed, Moved on, In progress), each opening its page. The date, level, and (In progress only) "2 of 3 done" (answers passed on the latest try, which with the lock is every question passed so far, out of the question count) share one meta line: only the parts present, dot separators hidden from screen readers. Empty: "No readings yet" with Start a new reading.
6. Prompts: a self-learner's question writes and effort checks use the solo system prompts (`SOLO_QUESTIONS_SYSTEM_PROMPT`, `SOLO_EFFORT_SYSTEM_PROMPT`, picked with `audience: "solo"`), which say the reader chose the reading and never mention a teacher or students; every rule, the output format, the grade level guidance, and the nudges are the same, and the class prompts are unchanged.

**Later (not v1):** saved reading libraries (paid), unlimited classes (paid), billing, a paid self-learner plan, the browser extension, and export to Google Classroom.

## Data model (Postgres / Neon)

| Table | Key fields |
|---|---|
| teachers | id, clerk_user_id, name, email, plan (free/paid), created_at, role (teacher/self_learner, null until chosen), age_confirmed_at (when a self-learner confirmed 13+; check: no self_learner without it). Every Clerk account, teacher or self-learner. |
| classes | id, teacher_id, name, grade_level, join_code (unique), code_active, created_at |
| readings | id, class_id, title, source_url, body_text, grade_level (overrides the class; optional), question_count, question_mode (shared/per_student), status (draft/published), created_at |
| questions | id, reading_id, student_id (null when shared), position, prompt, created_at |
| students | id, class_id, first_name, last_initials, name_key (unique per class, normalized), session_token_hash (SHA-256 of the cookie token, unique), created_at |
| student_question_calls | id, reading_id, student_id, created_at, given_back. One row per AI call for a student's own question set, for the "Try again" limit (created_at equals the claim's claimed_at, so a given-back failure marks exactly its row given_back). Every row counts toward the 10-minute window; only rows not given back count toward the 6. Kept until the student or reading is deleted, or the teacher uses Let them try again. |
| reading_cap_raises | id, reading_id (unique), teacher_id, from_limit, to_limit, raised_at. The one-time raise of a per-student reading's student set cap (150 to 300), and its log. |
| join_attempts | id, key_kind (ip/code), key_hash, created_at. Per-IP keys are HMAC-SHA256, per-code keys SHA-256; pruned after the 10-minute window. |
| attempts | id, student_id, reading_id, try_number (1 to 3, or more after a teacher's one more try), result (pass/fail), created_at |
| answers | id, attempt_id, question_id, text, ai_pass (bool), ai_feedback |
| challenges | id, student_id, reading_id, round (1, then +1 per new note after one more try), note, status (open/approved/denied/closed), resolved_at, resolved_by (the teacher; null for an auto-close), tries_allowed and checks_allowed (set only by Deny with one more try, or Give one more try on a no-note row), created_at. Unique per student, reading, and round. Give one more try without a note saves a round of its own: status denied, an empty note (a student's note is never empty), resolved_by the teacher, and the grant; it is never shown as a note, and the queue numbers a later note by the notes alone ("Note 1, after one more try"). |
| effort_checks | id, student_id, reading_id, created_at, finished_at, outcome (pass/fail/error/given_back). One row per effort check started: the in-flight claim while unfinished, and the per-student, per-reading check counter (given_back rows don't count toward it, only toward the outage window). Kept, no answer text. |
| self_readings | id, account_id (teachers, cascade), title, source_url, body_text, grade_level, question_count, status (in_progress/passed/moved_on), finished_at, questions_claim_token, questions_claimed_at, slot_released_at, created_at. A self-learner's reading; also the allowance's creation log (rows with slot_released_at set don't count). |
| deleted_clerk_users | clerk_user_hash (SHA-256 of "deleted-clerk-user:" and the Clerk user id), deleted_at, clerk_deleted_at (when Clerk's delete was confirmed; null while pending). Deleted accounts, so a late `user.created` or a leftover session can't recreate them. Confirmed rows are pruned 30 days after clerk_deleted_at by a later delete; pending rows (an under-13 delete, or a `pnpm ops:sweep-roleless-clerk-users` delete, whose Clerk call failed) are never pruned, and `pnpm ops:list-pending-clerk-deletes` lists them. |
| self_questions | id, reading_id (self_readings, cascade), position (unique per reading), prompt, created_at |
| self_attempts | id, account_id (cascade), reading_id (cascade), try_number (1 to 3, unique per reading), result (pass/fail), created_at |
| self_answers | id, attempt_id (self_attempts, cascade), question_id (self_questions, cascade), text, ai_pass, ai_feedback |
| self_effort_checks | id, account_id (cascade), reading_id (cascade), created_at, finished_at, outcome. Same role as effort_checks. |

Self-learner data has its own tables, never class or student rows, so a self-learner query can't reach class data and deleting the account reaches all of it. Every foreign key is ON DELETE CASCADE (none SET NULL or RESTRICT). A self-learner reading's status is set in the same transaction as the try that decides it.

Student status for a reading is derived from attempts, effort checks, and the latest challenge round, by one function for both the student and the teacher: **Passed** if any attempt passed or the latest challenge was accepted; **Challenged** if it is open; **Challenge denied** if it was denied without one more try; **Waiting** once every try (including a granted one more try) or every effort check is used with no pass and no note since, the same rule that replaces the answer form with the note box; **In progress** after any try, or after a denial with one more try not yet used; else **Not started**. Students see Waiting as "Send your teacher a note" (the next step is theirs, a note, though the teacher can also give one more try) and Challenged as "Waiting for your teacher"; teachers see "Waiting for teacher" and "Challenged".

## Key rules
- An attempt passes only when **every** answer passes the effort check.
- Try 4 is blocked; only the challenge option appears (unless the teacher gives one more try, below).
- Answers: each is trimmed and cleaned (control characters removed), then must be 1 to 1,000 characters. Try 1 answers every question, in one submit; after a failed try, the last answers are filled back in, with each answer's result and nudge.
- Passed questions are locked (PR 15, for students and self-learners alike): once a question passes the effort check it stays passed, with its answer as it was. Later tries (including a teacher's one more try) show it read-only, as done ("This one passed, so it’s done. No need to change it."), and answer, send, and check only the questions that are not yet passed; the effort check gets just those (fewer items, same prompt). The try passes once they all pass, and the reading's result counts every question. Enforced on the server: a submit must answer exactly the open questions (one that also answers a locked question, from an old tab or a crafted request, is refused as out of date, before any claim or model call); the claim only goes ahead while the student has exactly the tries the answers were checked against; and the commit copies the locked answers (text, pass, no nudge) from the previous try into the new one from the database, then inserts the new answers without ever replacing a locked one. So every try holds every question, and the latest try always says where things stand (the class list, history, the challenge queue, and the page all read it). "Passed" is derived from the saved answers (passed on the latest try), with no new column or migration. Counting is unchanged: one check per try, only checks the model answered count, and given-back failures use neither a try nor a check. Challenges are unchanged: the note opens after the last failed try or at the check limit, and the teacher sees every answer of the last try with its result.
- One effort check (one AI call) per attempt covers every answer. At most 1 check runs at a time per student and reading; a second submit meanwhile is told to wait.
- Effort checks per student per reading, for all time: **6 by default, +2 per teacher grant** (each "Deny, give one more try", or Give one more try on a no-note row, sets the limit to checks used + 2). The 6 are the 3 tries plus room for AI failures. Only checks the model answered count (PR 15): if the model replied but not usably (no tool call, the wrong answers, a refusal), the try isn't used up but the check counts; if the call failed with no reply at all (not set up, out of AI Gateway credits (402), another gateway refusal, an outage or 5xx, a network error, or a timeout), the try isn't used up and the check is **given back** (outcome given_back) and doesn't count either, for students and self-learners alike. Either way the student is asked to wait a minute before trying again. Given-back checks count toward a short outage window instead: at most **3 given-back checks per student per reading in 10 minutes**, counted under the same lock as the claim; past that the student sees an amber note, "Checking answers isn’t working right now, so let’s take a short break. This didn’t use up a try. You can try again at 2:40 PM.", and no model call is made. A check whose result couldn't be saved (a database error) also counts without using a try: a save that always fails must not become an endless loop of paid checks. Its claim is finished right away, so the student isn't told "still checking" for 90 seconds. Once every allowed check is used without a pass, the answer form goes away (even with tries left) and the challenge note opens instead.
- Challenge note: 1 to 500 characters, cleaned like answers. Only with no pass, once out of tries or effort checks (the student's own limits), with no open, accepted, or plainly denied challenge, and only one open at a time.
- A note can't be sent while an effort check is still running for that student and reading (for example the last allowed check in another tab, which could still pass): the student sees "We’re still checking your answers. Try again in a minute." The note insert takes the same lock as the check, so nothing slips in between.
- Accept and Deny: only the owning teacher, only while the challenge is open. One decision per challenge: a double-click or a second tab gets "Already decided" and the list refreshes. Ownership, "still open", and the grant are checked in the same transaction as the update. Nothing is deleted: attempts, answers, effort checks, and the challenge all stay.
- Deny, give one more try (its own button, so it can't be left ticked and ignored on Accept): the student gets exactly 1 try left, and effort check headroom for it: tries allowed become tries used + 1, and checks allowed become checks used + 2 (1 for the try, 1 spare for an AI failure). A student who reached the check limit with tries unused also gets exactly 1 try (not their unused ones back). Granting twice at once applies once.
- Give one more try on an "Out of tries, no note yet" row: the same grant with no note needed. Only the owning teacher, for a student in that class on a published reading of that class, and only while the student is still out of tries (or checks) with no note: no pass, no open, accepted, or plainly denied note, and no effort check running (then the live region says "Name’s answers are still being checked. Try again in a minute." and nothing changes). Checked in one transaction under the student's lock, like a note. After it the student has a try, so a second grant waits until that try is used too, exactly as "Deny, give one more try" needs a new note: never more tries than that path. A double-click, a second tab, or a note sent at the same moment saves only one of them; the loser hears "Nothing to change. The list is up to date."
- After one more try: if it passes, the reading is Passed. If it fails (or both checks fail on our side), the student can send a new note, which is a new challenge round; the teacher decides it like the first, and may give one more try again. Earlier rounds keep their decision.
- A challenge from a student who passes later is closed in the same transaction as the passing try (status closed), and the queue never lists a student who has passed.
- Copy and paste blocking (the reading text and the answer boxes: copy, cut, paste, drag and drop, and the context menu; on the reading text also select all and text selection) is a speed bump, not security. In an answer box, select all and selecting work, so select all + Delete clears an answer (blocking them made the old text stay and glue onto the new one); the selected text still can’t be copied, cut, or dragged out. A determined student can get around it; the effort check is the real gate. The trade-off: blocking selection also breaks select-to-read tools (Read&Write, the browser's read-selected-text) and right-click spellcheck in the answer boxes. A teacher setting to turn it off may come later.
- Unsent answers are kept as drafts in the browser's local storage (students and self-learners), keyed by ids only (mode, reading, student or account, try, question) with only the answer text and its saved-at time as the value (`{"savedAt": ms, "text": ...}`), and restored on reload. A draft older than 7 days (`DRAFT_TTL_DAYS`) is treated as absent, and each answer or note form prunes every expired unpack draft on the device when it loads; a draft in the earlier format (bare text, no time) loads as fresh and the prune stamps it, so it expires 7 days later (PR 16). A saved-at time in the future (a clock that was ahead) counts as saved now, and the prune re-stamps it with now, so it still expires 7 days later (PR 16 review N4). A check that saves drops that try's drafts (the page moves to the next try); a reading past answering drops all of them. The note to the teacher is kept the same way (key `unpack:note:v1:class:<reading>:<student>`, note text and saved-at time, same 7 days), restored on reload, and dropped once it is sent or the note box is gone. Blocked or full storage just means no drafts. See docs/privacy.md.
- Shared mode: questions are cached per reading. Per-student mode: each student's set is generated once and cached, and it isn't regenerated on retries.
- Shared mode: the question count stays the teacher's number. Deleting a question lowers it by 1 (never below 1), and publishing needs exactly that many questions. Changing a draft's text, grade, count, or mode clears its shared questions.
- Once published, the text, grade, question count, mode, and questions stay locked. This applies to both modes, and a later change to the class's grade doesn't move a published reading's grade (see the grade rule below).
- Title edits after publish: the title is the one thing that can still be edited once a reading is published (Edit title on the reading page), in both modes.
- Per-student mode, "Try again" limit: a failed question write saves nothing, and the student sees "Try again". At most **3 calls per student per reading in 10 minutes**, counting every call, including the given-back ones below; past that the student sees an amber note, "We tried a few times to get your questions ready, so let’s take a short break. You can try again at 2:40 PM." At most **6 counted calls for all time** (given-back calls don't count here); past that, "We couldn’t get your questions ready. Ask your teacher to let you try again." with a Try again button, and the teacher sees Needs a reset. The count is taken under the same lock as the claim, so a burst of Try agains makes exactly the limit of calls.
  - What counts toward the 6: only an AI call that reached the model and got a response back, including a response we then reject as unusable (no questions, wrong count, a refusal), and including a write whose first response was unusable and whose second try then failed. An open that finds the set, waits on another tab, or is refused adds nothing.
  - What is given back (the provider's or our setup's fault, not the student's): an API error with no response from the model (400 bad request, 401 bad key, 402 out of AI Gateway credits, 403 no permission, 404 unknown model, 429 rate limited, 529 overloaded, any other 5xx), a network error, or a timeout (the 30-second request timeout or our 110-second write deadline). It doesn't count toward the 6, but it does count toward the 3 per 10 minutes, so an outage can't be hammered: during one, a student gets 3 calls (one at a time), then the break message, then 3 more after the window, and never "ask your teacher". The call's row is written before the call, so a call in progress holds its place and a burst still can't get past the limit; when it ends this way, its claim is deleted and its one row is marked given back, together. Each failed call costs no model tokens, except a timeout, which may. With no AI Gateway credentials at all, nothing is called and nothing is recorded.
  - **Let them try again** (owning teacher only): clears that student's counted calls for that reading, so they get the full 3 per 10 minutes and 6 in all again. One statement, with ownership (the class is the teacher's, the student and reading are in it) checked in it; another teacher's request or ids outside the class change nothing ("We couldn’t do that. Please try again."). A call still running keeps its row. A repeat click is a no-op success. Questions, tries, and answers are untouched. Success says "Done. {name} can try again now."
- Per-student mode: each reading allows at most 150 student question sets. Past that, a new student sees "Ask your teacher for help with this one." A student who already has a set keeps it.
- Raising the limit (owning teacher only, published per-student readings only): one bump per reading, from 150 to 300, saved as a `reading_cap_raises` row (who, when, from, to) with the reading unique, so concurrent raises save exactly one; a second raise changes nothing and says "The limit was already raised to 300 students." The button shows from 135 sets (90%) so a teacher can raise it before anyone is turned away. The student set claim reads the raised limit under the same reading lock, so the cap stays exact (never over 150 before, never over 300 after). The student's message at the cap is unchanged.
- Deleting a reading (owning teacher only): one statement deletes the reading row, with ownership (the class is the teacher's, the reading is in it) checked in it, and the database cascades to everything under it in the same transaction: its questions (shared and per-student), answers, question generation rows, AI call counts, tries, effort checks, challenges, and its limit raise. Students and their other work stay. Deleting again is a quiet success (back to the class page); another teacher's class is "We couldn’t delete that reading. Please try again." and changes nothing.
- Class settings (owning teacher only): the name is trimmed and 1 to 60 characters, and the grade one of the grade levels, the same checks as creating a class. Name and grade save in one transaction, with ownership checked in it. A grade change clears and pins what the grade rule below says; a same-grade save (a name change, say) clears and pins nothing.
- Changing a class's grade clears the shared questions of its draft readings that use the class grade (no reading override); those drafts follow the new grade. Published readings keep the grade they were published with: in the same transaction, before the class's grade changes, each published reading with no grade of its own gets the old class grade written onto it (read from the locked class row), so per-student sets and effort-check nudges for it are still written for that grade. Published readings with their own grade, and drafts with an override, are untouched. Before saving, the settings form says how many drafts would be cleared; after, "Saved. Cleared the questions of {n} draft readings."
- Question generation is limited to 30 per teacher per 10 minutes (generate, regenerate, and previews). Students' own sets in per-student mode don't count toward it. A self-learner's question writes count toward the same per-account limit. Past it, the teacher sees an amber note: "You’ve written a lot of questions in the last 10 minutes, so question writing is taking a short break. You can try again at 2:40 PM."
- Free plan: creating a 2nd class is blocked.
- Readings: the text must be 200 to 20,000 characters after cleanup (line endings, control characters, extra blank lines). A longer article is refused, never cut. Titles are up to 120 characters, links up to 2,048.
- Link fetching: limited to 20 per teacher per 10 minutes (pasted text isn't limited). Past it, an amber note under the link: "You’ve added a lot of links in the last 10 minutes, so adding by link is paused for a bit. Pasted text still works. You can try again at 2:40 PM." with the "Paste the text instead." control. We only fetch http/https links to public hosts, with 8 seconds and 2 MB per fetch, and only HTML pages.
- Joining: a student enters the class code, their first name (up to 30 letters; spaces, hyphens, apostrophes, and the ʻokina are OK), and the first 1 or 2 letters of their last name. Nothing else is collected.
- First names start with a letter, or with one ʻokina or apostrophe before a letter ("ʻIolani", or "'Iolani" from a keyboard without an ʻokina). They end with a letter, never start with a hyphen, and can't be only marks or punctuation.
- A name already taken in the class is refused with "Someone already has that name. If it’s you, open unpack on the device you joined with, or add another letter." It is never resumed: progress does not carry over by name. "Taken" compares a folded key: case, extra spaces, apostrophes and the ʻokina, and Latin accents are ignored, and a hyphen counts as a space. So "Keʻala" and "Keala", "Zoë" and "Zoe", "D’Andre" and "DAndre", and "Jean-Luc" and "Jean Luc" are the same name; "Mary Ann" and "Maryann" are not. What the student typed is what the teacher sees.
- Changing the folding changes every name key. Existing students keep their old keys until they are recomputed with `pnpm db:recompute-name-keys` (a dry run unless ALLOW_DB_WRITES=1; names that now collide are counted and left as they are, for the teacher). No real data exists yet, so nothing needs recomputing for this change.
- Joining needs the class code to be on. An unknown code and a code that's off get the same message ("We couldn’t find that class code. Check it with your teacher."). Students who already joined keep access when the code is turned off, and when it is replaced: a session is tied to the student and class, never to the code.
- Join code on/off and New code: only the owning teacher (checked in the update itself). On/off saves the value asked for, so a double click lands where the teacher pointed. New code is one update, retried with a fresh code if another class has it; concurrent New codes end with exactly one current code, and the old code stops working as soon as it commits. Neither is destructive (no red), but New code asks for a quick confirm because the old code stops working.
- Joining is rate limited to 60 tries per IP and 100 per code, each per 10 minutes. Every try that passes the bot check counts, including a wrong code or a taken name. Past a limit, the student sees an amber note naming which one: "Lots of people have tried to join from here in the last few minutes, so joining is paused for a bit." or "This class code has had lots of tries in the last few minutes, so it’s paused for a bit.", then "You can try again at 2:40 PM." (the later of the limited keys' oldest counted try plus 10 minutes).
- Bot check on joining (Cloudflare Turnstile, widget mode Managed: Cloudflare decides whether to show an interactive check or pass silently). On when both `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are set. Setup (same rules as `JOIN_IP_HASH_SECRET`; production means `NODE_ENV=production` or `VERCEL_ENV=production`):
  - Production: both keys are required. With either (or both) missing, every join is refused with "Joining isn’t working right now. Please try again in a little while." and the server logs one error per refused join, tagged `join_blocked_config`, naming the missing variable (never a value). It fails closed so a forgotten key can't quietly turn the check off.
  - `TURNSTILE_DISABLED=1` (exactly `1`): the check is off, keys or not. In production this is the only way to run without it, an explicit opt-out, and every join logs a warning that the check is off (each time, not once per process: serverless processes are short-lived, so a once-only warning would be easy to miss).
  - `TURNSTILE_DISABLED` is meant to be temporary: an emergency switch (Cloudflare down, a broken widget), not a permanent setting. Remove it as soon as the problem is fixed; production runs with the check on.
  - Local dev and tests: neither key means off (no widget, no server call; joins rely on the rate limits). Cloudflare's public test keys (in `.env.example`) turn it on locally. Only one key set refuses every join anywhere.
  - Hostname: the token must have been solved on one of `TURNSTILE_EXPECTED_HOSTNAMES` (comma-separated). If that's unset, production on Vercel uses the deploy's own hostnames (`VERCEL_PROJECT_PRODUCTION_URL`, `VERCEL_BRANCH_URL`, `VERCEL_URL`); otherwise the hostname isn't checked. Vercel Preview builds run with `NODE_ENV=production`, so this applies there: set `TURNSTILE_EXPECTED_HOSTNAMES` on Preview if previews use a custom domain. Never checked with Cloudflare's test secret keys (their replies say "example.com"). A mismatch is refused like a failed check.
  - Action: the token must carry the join's action (`join`). Only Cloudflare's test secret keys may reply with an empty or missing action.
- When the bot check is on, the widget sits under the form fields, and the server verifies its token with Turnstile's siteverify (5-second timeout; only the secret and the token are sent, never the student's IP). It fails closed: a missing token gets "Finish the check above the button, then try again."; a failed, expired, or reused token, a token made for another action or another hostname, a timeout, a network error, or a reply that isn't JSON gets "We couldn’t check that you’re a person. Try again in a moment." Order: form validation, then the server setup check (below), then the bot check, then the rate limits, then the join, so a bot that can't pass the check can't use up a code's or a school's tries. Each token is single use; the widget resets after every submit.
- Clerk webhook (`/api/webhooks/clerk`, public, signature-checked with `CLERK_WEBHOOK_SIGNING_SECRET`): `user.created` upserts the teacher by Clerk user id (name from first and last name, email the primary address), the same upsert as a first visit, so the two can't make two rows. `user.updated` only updates an existing teacher row and never inserts: deliveries can arrive out of order, so a late `user.updated` after `user.deleted` finds no row and is a 200 that changes nothing (a teacher who never visited gets their row on first visit). `user.deleted` deletes, in one transaction, the account's classes first (which cascades to their readings, students, and all student work, resolved challenges included), then its self-learner readings (which cascade to their questions, tries, answers, and effort checks), and then the account row (which cascades to the account's own logs). `user.created` never sets a role: the account chooses on `/welcome`. The order matters: one delete of the teacher row would also try to clear `challenges.resolved_by` on challenges the same delete is removing, and fail. The account is gone, so nobody can sign in to see that data again, and keeping it would only keep children's data longer. In the same transaction it lists a SHA-256 hash of the Clerk id in `deleted_clerk_users` as confirmed (PR 15; it also confirms a pending under-13 row, and prunes confirmed rows 30 days past their confirmation). `user.created`, `user.updated`, and the first-visit creation refuse a listed id inside their own statement, so a late delivery or a session that outlived the account never recreates the row: the webhook still answers 200 (outcome deleted_account) so Clerk stops retrying, and the person lands on `/account-deleted` ("This account was deleted", with Sign out). That is only while the Clerk user still exists (for example an under-13 delete whose Clerk call failed: the listed hash refuses the row, and the Clerk delete is retried first); if Clerk has already deleted the user, the session can't load it (Clerk answers 404) and the visitor goes to `/sign-in`. A repeat `user.deleted`, or one for a user who never visited, is a 200 that changes nothing (the hash is listed either way). A user with no email is skipped, other events are ignored (200). A bad or missing signature is a 400 with no detail; no secret is a 500 with a server log. Logs carry only the event type and outcome.
- Bot check on teacher sign-up: Clerk's own **Challenge suspicious sign-ups** (Clerk Dashboard, Protect, Protections; Clerk docs: clerk.com/docs/guides/protect/bot-protection, read Oct 27, 2026). We don't control Clerk's sign-up page, so we add no widget and no keys for it. What it covers:
  - It's on by default for new Clerk applications and included on every plan. At deploy, check that its row on the Protections page says Active. An older application may instead show a legacy "Bot sign-up protection" row; enable that or take Clerk's Update to the new one.
  - Sign-ups only. It never challenges a sign-in. Teacher sign-in has no bot check of ours (Clerk's own sign-in protections, such as locking accounts after failed sign-ins, are Clerk settings).
  - With the default setting (Suspicious), only sign-ups that Clerk flags as automated, or that come through a VPN, Tor, or a residential or data center proxy, are challenged; other sign-ups see nothing. Challenging every sign-up ("All") needs Clerk's Business plan.
  - A challenged sign-up runs a Cloudflare Turnstile check in the browser (usually invisible, sometimes a CAPTCHA). Our prebuilt `<SignUp />` shows it inside the form. If it fails, no account is created, so no `teachers` row is ever made for it.
  - Our Turnstile keys cover the student join only.
- Where Turnstile loads: ours only on `/join`, only when the bot check is on (the page picks the site key on the server with `botCheckSiteKey()`; off or misconfigured renders no widget and no script, and no layout or other page loads it; `src/app/join/turnstile-scope.test.ts` pins this). Clerk's loads separately, on any page with `ClerkProvider` (all of them): besides the sign-up challenge, clerk-js runs a "captcha heartbeat" from `Clerk.load()` that, when Clerk turns `captcha_heartbeat` on for the instance (its environment's display config, not an option we can set), solves an invisible Turnstile (action `heartbeat`) right away and every 10 minutes and sends the token to Clerk. That's why a signed-in page like `/welcome` can show Turnstile even with `TURNSTILE_DISABLED=1`. Clerk-js also runs a Turnstile on any page when Clerk answers a request with `requires_captcha`. We leave both alone: they are part of Clerk's bot protection, which stays on.
- Expected console noise: Turnstile's iframe (`challenges.cloudflare.com`) can log errors like "Connecting to 'data:,' violates the following Content Security Policy directive: connect-src ...". That is Cloudflare's own CSP on its own iframe, not ours (we send none), so we can't change it and shouldn't. Cloudflare's CSP reference doesn't ask sites to allow `data:` in connect-src.
- If a Content-Security-Policy is ever added, allow `https://challenges.cloudflare.com` in script-src and frame-src (our Turnstile and Clerk's sign-up challenge and heartbeat all need it; Clerk lists its own CSP requirements). Cloudflare also asks for `'self'` in connect-src only for Turnstile pre-clearance, which we don't use. There is none today (`turnstile-scope.test.ts` checks that too).
- Limits and retry times (PR 15): every rate-limited state is a calm amber note (never red, `role="status"`) that says what happened and what to do, without jargon, and ends with when the next try frees up: the oldest counted attempt in the window plus the window, formatted on the server in the visitor's zone from Vercel's `x-vercel-ip-timezone` (else UTC, labeled "UTC"): "You can try again at 2:40 PM." (today), "... tomorrow at 9:00 AM.", "... on Friday at 9:00 AM.", "You can try again in a minute." when it's under a minute away. When the time can't be read, it says "Try again in a few minutes." The same helper (`local-time.ts`) formats the weekly allowance. Limits with no time to wait out (the 6 checks, the 6 counted question calls, a reading's student cap) keep their "ask your teacher" or "move on" copy.
- These limits are first estimates. A school behind one shared IP can hit 60 tries per IP if several classes join at once. With the bot check on, junk tries on a real code need a solved check each, which makes blocking a code for 10 minutes much harder; a teacher can also make a New code. The numbers stay as they are until real use says otherwise.
- Server setup check on joining: before the bot check's network call or any database work, a join is refused with "Joining isn’t working right now. Please try again in a little while." when the Turnstile keys are misconfigured (above) or, in production, `JOIN_IP_HASH_SECRET` is missing, shorter than 32 characters, or the `.env.example` or dev-only value. Each refused join logs one `console.error("join_blocked_config", { missing, message })`: `missing` lists the variable names (never a value), `message` explains. Other failures keep their messages: a database error still gets "We couldn’t join you to the class. Please try again."
- IP addresses are stored only as a keyed hash (HMAC-SHA256 with a server secret), only for the join rate limit. Rows are deleted by the next join after the 10-minute window (so after a quiet period they can stay longer), and Neon's restore history keeps deleted rows for its restore window.
- A student's session is an httpOnly cookie that lasts 180 days. Only a hash of its token is stored. Joining a different class on the same device replaces the session.
- Student data is visible only to the owning teacher, and we store only first names plus last initials. Exactly what is stored, who sees it, and how long it stays: [Student data and privacy](privacy.md).
- Deleting a student (owning teacher only): one statement deletes the student row, with ownership checked in it, and the database cascades to everything under them in the same transaction: their own question sets and generation rows, AI call counts, tries, answers, effort checks, and challenges. Their session ends with the row. Other students are untouched. Deleting again, when the class is the teacher's but the student is no longer in it, is a no-op success (we keep no list of deleted ids, so an id never in the class gets the same answer and changes nothing). Another teacher's class is "We couldn’t delete that. Please try again." and changes nothing. Neon's restore history keeps deleted rows until its window passes.

## AI calls
1. **Generate questions** (once per reading, or once per student in per-student mode): open-ended questions tied to specific details in the text, plus one "what do you think" question, written for the teacher-chosen grade level.
2. **Effort check** (per attempt): one call, given the text and every question with its answer, returns pass or fail per answer and a nudge on each fail. The bar is "did they try and engage with the text and the question," never quality, spelling, grammar, or correctness. Short but genuine answers and opinions pass; "idk", gibberish, a copy of the question, and off-topic answers fail. It writes for the reading's grade (the reading's own grade, else the class's), and treats the text and answers as data, never as instructions.
   - Nudges: at most 140 characters, kind and specific (what to look at or add), never giving away an answer, never shaming. Dashes are removed and longer nudges are shortened before a student sees them.
3. **How the calls are made** (PR 14): through **Vercel AI Gateway** with the AI SDK (`generateText`), still Claude. The model is `anthropic/claude-sonnet-5.5` unless `AI_MODEL` says otherwise (the old `ANTHROPIC_MODEL` is still read; a bare Anthropic id like `claude-sonnet-5-5` becomes `anthropic/claude-sonnet-5.5`). Requests are routed to Anthropic only (the gateway's `only: ["anthropic"]`), not to other hosts of Claude. This is deliberate and should stay: the requests carry children's writing, so fewer processors wins over availability (when Anthropic is down, the call fails and the try is given back instead of going to Bedrock or Vertex AI). See [privacy](privacy.md).
   - Credentials: an AI Gateway API key (`AI_GATEWAY_API_KEY`) if set, else Vercel OIDC: on a Vercel deployment the token comes with each request and needs no env (AI Gateway must be enabled for the project); for local dev, `vercel env pull` writes `VERCEL_OIDC_TOKEN` (it expires after 12 hours). A key, if set, always wins. With neither, nothing is called: teachers see "Question writing isn’t available right now. Trying again soon won’t help, so please check back later.", the student's or self-learner's try is given back, and the server logs an error naming what's missing (never a key or token).
   - Each call: the system prompt, one user message, and one strict tool (`submit_questions` or `submit_effort_check`) with auto tool choice and parallel tool use off, low effort, and up to 8,000 output tokens for questions and 6,000 for the effort check. The tool isn't forced (a forced tool is a 400 on current models with thinking), so a reply without the call is invalid output. Every reply is validated with zod, and invalid output gets one more call with a note on what was wrong.
   - Time limits: 30 seconds per request, one SDK retry (network errors, a request timeout, 408/409/429/5xx), and one overall deadline: 110 seconds for a question write and 60 seconds for an effort check, covering both validation attempts, the retry, and its wait. A deadline or request timeout shows "That took too long. Try again."
   - Failures: no credentials, a 401, 402 (the AI Gateway account is out of credits), 403, or 404 (unknown model) is not_configured; 429 or 529 (overloaded) is busy; 400, any other 5xx, and network errors are failed; timeouts are timeout.
   - What each screen says (src/lib/ai/errors.ts questionErrorClass): not_configured is **unavailable**, the rest are **transient**. Unavailable never invites a quick retry: teachers see "Question writing isn’t available right now. Trying again soon won’t help, so please check back later."; a student's per-student reader "Your questions can’t be written right now. Please come back later, or let your teacher know."; a self-learner's reader "Questions can’t be written right now. Your reading is saved, so please come back later."; the readers show no Try again button. Transient keeps its Try again: teachers see "busy … Try again in a minute.", "took too long. Try again." or "couldn’t write questions this time. Try again." (sets, samples, and replacement questions alike); students and self-learners "We couldn’t get your questions ready. Try again in a moment." with a Try again button. A provider outage shows up as busy (529, overloaded) or failed (5xx): one request can't tell an outage from a one-off error. Only a reply from the model (valid or not) counts toward a student's 6; everything else is given back, as above.

## Decided
- AI provider: **Claude** for both question generation and the effort check, through **Vercel AI Gateway** (PR 14; it was the Anthropic API directly before).
